# Windows applications, windows and paths

`platform.windows` contains local OS functions, independent of tools, reply generation and model providers. `tools.builtin.windows` exposes `appControl`, `windowControl` (windows, displays and virtual desktops), `openWebsite` and `openPath` through the existing builtin registry, selection, planner and tool execution paths.

## Availability

- Registration requires Windows and `windows_tools_enabled` (default `true`). The daemon applies availability at startup and builds the application index on a background thread.
- Each adapter also checks the setting before executing. Non-Windows imports are safe; OS libraries are loaded inside operations.
- OS operations run on a daemon worker with a twelve-second deadline. A timed-out request reports failure and is not retried automatically; a Windows call already in progress can still finish.
- `windows_app_aliases` maps friendly names to installed application names or discovered launch targets. Invalid entries are ignored. The user's configuration is not rewritten to add defaults.
- `windows_monitor_aliases` maps user labels to display device identifiers. `windows_window_zones` maps a device identifier to named zones, each `[x, y, width, height]` as fractions of that display's work area. Entries that are not text, or zones that fail validation, are unavailable and logged as counts only (never labels or identifiers). Defaults are not written and unknown keys are preserved. There is no configuration screen for these mappings; they are edited in `config.json`.
- `windows_fancyzones_enabled` (default `true`) lets placement use the zones of Microsoft PowerToys FancyZones (see Displays and placement). Turning it off leaves only configured zones. It is a Settings toggle on the Windows page.
- Routing reads the ready application index through a non-blocking snapshot. The application adapter exposes discovered names, user aliases, canonical launch names and executable stems to the deterministic matcher. Entries sharing an executable share a routing identity. An unready/failed index yields no targets without starting discovery or waiting.
- No new model context, command matcher, telemetry or proprietary service is required.
- Named workspaces (sets of browser windows and apps opened and placed together) build on this placement code and are specified in `workspaces.spec.md`.

## Applications

- The catalogue combines per-user and shared Start Menu shortcuts, current-user and machine App Paths in both registry views, and `Get-StartApps` application IDs. Discovery uses a fixed PowerShell script with an eight-second timeout, never user-supplied command text.
- Installed Steam games join the catalogue (`platform/windows/steam.py`). Steam's install folder comes from the registry; `libraryfolders.vdf` lists every library and each library's `appmanifest_*.acf` supplies a game's id and name. Only fully installed games count, and tooling Steam installs as apps (the Steamworks redistributables, Proton and Linux runtimes) is skipped. A game launches through `steam://rungameid/<id>`, so Steam does its own launching and updating, and it resolves like any other application name. A game whose name equals a Start Menu entry is not listed twice. Missing Steam, unreadable manifests and any other Steam failure leave the rest of the catalogue untouched. Games have no discovered executable, so their windows are matched by name tokens and `focus` and `close` need a window handle.
- Exact names take precedence, followed by discovered executable stems and whole Unicode tokens. Shortcut executable identities separate application launchers from their helper utilities. Matching is case-insensitive. Multiple distinct targets produce an ambiguity error rather than launching an arbitrary application.
- `open` launches the discovered target through Windows associations. Success means Windows accepted a launch request, not that application startup has completed.
- `open` with any placement field (`monitor`, `zone`, `state`) launches once and then places the application's window; without `monitor` the destination is the primary display (see Windows). The destination (display, zone, state) is validated before anything is launched. One monotonic deadline of ten seconds, inside the twelve-second operation limit, covers launch, window discovery and placement.
  - Windows belonging to the application are the visible, unowned, non-cloaked windows whose owning executable stem equals the catalogue entry's, or, for packaged applications with no discovered executable, whose title or process contains every token of the application name. A snapshot is taken before launching.
  - A window that was not in the snapshot and stays unchanged for half a second is the target, so a splash screen that is replaced is not chosen. If no new window appears within two seconds and exactly one matching window already existed, that window is reused (`reused_window: true`) for single-instance applications. Several candidates are never resolved arbitrarily.
  - The launch is never repeated. After an accepted launch every non-success is a structured partial failure with `launch: accepted` and `placement` set to `failed` (with the `hwnd`), `unverified` (no matching window appeared in time) or `ambiguous` (with candidate handles, titles, processes and process IDs). The result carries `success: false`; the registry does not retry builtin tools, so no retry can launch again.
  - Success returns `action: opened_and_placed`, `application`, `hwnd`, `process`, `pid`, `monitor`, `zone` (when requested), the verified `rectangle`, `state` and `reused_window`. Plain `open` returns `open_requested` with the application name. Just before launching it lists the application's windows that are already open (one listing, no waiting), so the window the launch produces can be identified later (`track_launch`, see `memory/desktop_referents.spec.md`).
- `focus`, `close` and `list` operate on visible unowned top-level windows. Cloaked windows are excluded using Desktop Window Manager (`DWMWA_CLOAKED`) attributes so cloaked UWP or shell windows are not listed or matched. If DWM attribute queries fail, the check fails gracefully without aborting enumeration. The target can be an executable stem, window title or decimal window handle from the listing. Multiple matches require an explicit handle. With `match: process` (set by fast routes) only the executable stem or handle can match.
- Aliases for existing windows resolve through the application catalogue to the executable stem. Packaged aliases without a discovered executable require an explicit window handle.
- Results of `focus`, `close`, `minimise`, `maximise` and `restore` carry the window's `hwnd` and `process`.
- Successful `appControl` and `windowControl` actions (and a launch whose placement failed) record a desktop referent: application, process, handle, display, zone and state, never titles or paths. `list` and `displays` record nothing. See `memory/desktop_referents.spec.md`.
- `close` posts `WM_CLOSE`. It neither kills processes nor suppresses application save prompts. The result says `close_requested`, because the application owns completion.

## Windows

- `windowControl` supports `minimise`, `maximise`, `restore`, `list`, `displays` and `place`. Actions use pointer-sized Win32 API signatures and verify the resulting show state with a bounded wait.
- `displays` (empty target) returns the connected displays: device, `number` (the value that selects it as a monitor reference), primary flag, bounds, work area, the configured aliases that name it and its configured zones as pixel rectangles. When FancyZones has a usable layout for a display it also carries `fancyzones`: the `layout` type and its `zones`, each with the `names` it answers to (its 1-based number first, then derived position names) and its pixel `rectangle`. Names a configured zone already uses are not listed. Aliases and zones for disconnected devices are omitted, and nothing else from the configuration, and no PowerToys identifiers or paths, are returned.
- `place` takes `target` (an application name, alias or window handle, resolved like the other window actions), an optional `monitor` (a device identifier, configured alias or built-in reference; the primary display when omitted), an optional `zone` (a configured label or a FancyZones name or number for that display, case-insensitive) and an optional `state` (`restore`, the default, or `maximise`). Without a zone the window keeps its size; `maximise` fills the display's work area and cannot be combined with a zone. The result is `action: placed` with `hwnd`, `process`, `pid`, `monitor`, `zone`, the verified `rectangle` and `state`.
- The placement fields `monitor`, `zone` and `state` exist only on `windowControl place`, `appControl open`, `openWebsite` and `openPath`. A placement without `monitor` (a zone or state alone, or a bare `place`) uses the primary display, exactly as `monitor: "primary"` would; the result names the display used. Any other combination (a placement field on another action, `displays` with a target or fields, an unknown zone, an unknown or disconnected display) is rejected before any window is launched or moved. Empty-string placement fields count as absent.
- Focus restores a minimised window, requests foreground activation and checks the foreground handle. Input queues are temporarily attached when necessary and always detached. Windows permission or foreground restrictions produce a failure rather than a success claim.
- `windowControl` also drives virtual desktops (`platform/windows/virtual_desktops.py`, over `pyvda`, which carries the shell interface identifiers for each Windows build including 24H2). Desktops are numbered from 1 in the order the shell lists them. The actions take an optional `desktop` argument, which no other action accepts, and an empty `target` except `move_to_desktop`.
  - `desktops` reports the `count` and the `current` desktop. `desktop_switch` goes to a number, `next` or `previous`; it never wraps, and a desktop that does not exist is an error naming the valid range. Switching to the current desktop changes nothing. `desktop_new` creates a desktop and switches to it, as Windows' own shortcut does. `desktop_close` closes the named desktop, or the current one without `desktop`; the last desktop cannot be closed, and the windows on a closed desktop move to a neighbour, none is closed. `move_to_desktop` resolves its target window like the other window actions and moves it, leaving a desktop referent (`move_desktop`).
  - Windows on other desktops are cloaked and so are not listed, which means `move_to_desktop` reaches windows on the current desktop. If `pyvda` is missing or the shell does not answer, every desktop action fails saying virtual desktop control is unavailable; keyboard shortcuts are never substituted.
  - Results are raw state: `action` (`desktop_switched`, `desktop_created`, `desktop_closed`, `moved_to_desktop`), `count` and `current`, or `hwnd`, `process` and `desktop`.
- Listing returns handles, titles, executable stems and process IDs of visible, non-cloaked windows. These are local data. Tool results and errors pass through the existing redaction function before model consumption; raw titles and paths are excluded from debug messages.

## Displays and placement

- `displays.py` enumerates connected monitors through Win32 (`EnumDisplayMonitors`, `GetMonitorInfoW`): device identifier (for example `\\.\DISPLAY1`), bounds, work area (taskbar excluded) and primary flag. Rectangles are `(left, top, right, bottom)` in physical pixels of the virtual desktop, so displays left of or above the primary have negative coordinates.
- Enumeration and measurement run inside a scoped per-thread DPI awareness context (per-monitor v2). The previous context is restored on every exit, and the process-wide mode, which Qt owns, is never changed. If the API is unavailable the scope is a no-op.
- `resolve_monitor` accepts a connected device identifier or a configured alias, case-insensitively, then a built-in reference. A decimal number counts the connected displays in Windows display-number order (the numbering Windows Settings shows), so `2` is the second display even when device names have gaps. `primary` is the primary display. `left` and `right` are the display whose centre is furthest in that direction, and need at least two displays and a single winner. These references are tool-argument vocabulary resolved from the structured `monitor` argument, never matched in an utterance; identifiers and configured aliases always win over them, so a user alias named `left` keeps its meaning. An empty or unknown label, an alias whose display is disconnected, and a label that could mean two displays are errors. No other display is ever substituted.
- A zone is `[x, y, width, height]`, fractions of a monitor's work area. Values must be finite real numbers, width and height positive, the origin within 0 to 1 and the rectangle wholly inside the work area. Edges are rounded rather than sizes, so adjacent zones tile exactly.
- `place_window(hwnd, monitor, rectangle=None, state='restore')` validates its arguments before touching the window. A minimised or maximised window is restored first. The visible frame (DWM extended frame bounds) is moved to the target by compensating for the invisible resize borders, re-measuring the borders on each of up to three attempts because a move between displays of different DPI makes the window rescale itself.
- Without a rectangle the window keeps its size, clamped into the destination work area: one already on the destination stays nearby, one arriving from another display is centred. `state='maximise'` moves the window onto the destination, maximises it and requires the frame to fill that work area; it cannot be combined with a rectangle.
- Success is reported only after verifying the show state, that the visible frame is within a two-pixel tolerance (`PLACEMENT_TOLERANCE_PX`, for native frame rounding) of the target, and that the window is on the destination display. A frame that differs in size reports that the application's minimum or maximum size prevents the placement. Rejected `SetWindowPos`, a window that closes meanwhile and an expired deadline are explicit failures. The optional `deadline` is a monotonic instant shared with the caller.
- The result is raw data: `hwnd`, destination `monitor`, the resulting `rectangle` and `state`. Debug messages never include titles or paths.

### FancyZones zones

- `fancyzones.py` is pure parsing and geometry over the files PowerToys writes in `%LOCALAPPDATA%\Microsoft\PowerToys\FancyZones` (`applied-layouts`, `custom-layouts`, `default-layouts`, `settings`). Jarvis only reads them and never writes. It imports nothing from tools, replies or models; `displays.py` supplies display identities, the current virtual desktop and the label vocabulary.
- Geometry reproduces PowerToys' own layout code, including integer rounding: columns, rows, grid, priority-grid and focus templates, and custom grid and canvas layouts. Spacing applies only when the layout shows spacing. Zone rectangles are computed from each display's work area and are the rectangles FancyZones snaps a window into. Canvas layouts are scaled in double precision, which can differ by a pixel where PowerToys' single precision lands within rounding error of a whole pixel.
- Layouts come from the current virtual desktop, found as PowerToys finds it (the Explorer `CurrentVirtualDesktop` value, then the session key, then the first listed desktop, then a single unnamed desktop). Only connected displays contribute, so entries for disconnected monitors and other desktops are ignored.
- A connected display matches a saved layout as PowerToys matches it: the monitor ids agree (the EDID-derived id, or the device name when Windows reports none), and the instance ids agree or the display numbers do; serial numbers veto a match only when both are known. The closest identity wins; two equally close entries with different layouts leave that display without zones rather than guessing. A display with no saved layout gets PowerToys' default layout for its orientation. A layout that cannot be computed, or a FancyZones setting that spans zones across monitors (unsupported), yields no zones for the affected displays.
- Zones are numbered from 1 in FancyZones order and always answer to their number. Derived names (`left`, `right`, `middle`, `top`, `bottom` and the four corners) are added only where exactly one zone qualifies: left and right need a full-height zone on that side, top and bottom a full-width one, middle a zone at the centre, and corners a zone in that quarter. A name that would fit two zones is offered for neither. The words are locale data in `zone_labels/<language>.json`, selected from `fast_commands_locales` plus English; languages without a file contribute no derived names, and numbers remain.
- Configured zones take precedence over FancyZones zones with the same name (including a configured zone named like a number). Resolution is case-insensitive, never guesses a near match, and an unknown name lists every usable name. FancyZones zones are read only when a zone is requested or displays are listed, never for a placement without a zone.
- PowerToys is optional. A missing folder, unreadable or malformed files, an unexpected failure or `windows_fancyzones_enabled: false` all leave placement exactly as it is with only configured zones. Debug messages carry counts and exception types only, never paths, monitor ids, instances or serial numbers.
- Placement through a FancyZones zone moves the visible window frame to the zone rectangle with the same verified placement as any other zone; it does not register the window with FancyZones, so FancyZones' own zone history and snapped-window tracking are not updated.

## Websites

`openWebsite` opens one web page, optionally in a new browser window placed on a display and zone, in one call. It is the only tool that opens web addresses; `appControl` opens browsers as applications and `openPath` refuses web addresses.

- Arguments: `url` (required), optional `browser` and the placement fields. `url` is an `http` or `https` address with a host, or a bare host such as `youtube.com` or `youtube.com/feed`, which is opened as `https`. Any other scheme (`file:`, `javascript:`, `data:` and so on), local paths, text with spaces, credentials in the address and a bare host without a dot are rejected before anything is launched.
- `browser` is one of the Chromium browsers workspaces support (`chrome`, `edge`, `brave`, `vivaldi`), resolved by the same `find_browser` (`workspaces.spec.md`, Browsers), never from user text.
- Without placement and without `browser`, the address opens through Windows' association for it, so the user's default browser shows it in its usual way (normally a new tab). With `browser`, that browser is started once with the address. The result is `action: website_opened` and `browser` (`default` or the browser's name).
- With any placement field, the destination is resolved exactly as for `appControl open` (primary display when no monitor) and validated before launching. The browser (`browser`, else the default browser when it is Chromium-based, else Chrome) is launched once with `--new-window` and the address, and the new window is found and placed by the same code as a workspace `browser_window` item: a snapshot of the browser's windows before launching, the one new window that stays unchanged for half a second, one ten-second deadline covering launch, discovery and verified `place_window`. Several new windows are never resolved arbitrarily.
- Success is `action: website_opened_and_placed` with `browser`, `hwnd`, `process`, `monitor`, `zone` (when requested), the verified `rectangle` and `state`. After an accepted launch every non-success is a structured partial failure (`success: false`) with `launch: accepted`, `browser`, `monitor`, `zone`, `placement` set to `failed` (with `hwnd`), `unverified` or `ambiguous`, and `reason`. The launch is never repeated.
- One browser window opens at a time: a website launch and a workspace launch share one lock, and a request that finds it held fails at once as busy, launching nothing, so two launches cannot mistake each other's windows.
- Results and debug logs never contain the address. A placed or partially placed window is recorded as a desktop referent with the browser's name as `application`.

## Paths

- `openPath` accepts a file path, folder path, `Desktop`, `Documents`, `Downloads`, `Pictures`, `Music` or `Videos`. A web address (`http`, `https` or `www.`) is rejected with a pointer to `openWebsite`, launching nothing.
- Searching by type or date, listing, reading and changing files belong to `localFiles` (`tools/builtin/local_files.spec.md`), whose `find` shares this section's index backends and noise rules and returns full paths that `openPath` accepts.
- Known folders use `SHGetKnownFolderPath`, respecting redirection and localisation. Existing paths open through Windows file associations.
- A target that is not a URL, a known folder or a path is a name to look up (**open anything**). Text with a path separator, a drive letter or a `~`, `%` or `.` prefix is a path and is never searched, so a missing path stays "not found". A bare name is never resolved against the working directory.
- **Saved names**: `windows_path_aliases` maps a name to the exact file or folder it opens (for example `"user manual"` to a PDF). A bare name is compared with the saved names first (Unicode-normalised, case-insensitive, whitespace-collapsed) and, when one matches, that path opens with no file search; a path-like target or known folder is never treated as a saved name. The saved path may use `%ENVVARS%` and `~`, and passes the same checks as any path (must exist, never a program or script), so a stale entry fails as "not found" rather than falling back to a search. Results report `source: alias`. Entries that are not non-empty text pairs are ignored and logged as a count. There is no settings screen; it is edited in `config.json`, and paths never reach logs.
- Name lookup (`platform/windows/file_search.py`) queries a local index and nothing else, trying the voidtools Everything SDK first when Everything is running and its SDK library (`Everything64.dll`, from a standard install folder) is present, otherwise the Windows Search index (`SystemIndex` over OLE DB through `pywin32`). Each backend runs on a bounded worker; one that fails or times out falls through to the next, and if none answers the tool reports that file search is unavailable. The query is split into letter and digit tokens that must all appear in the item name, so no user text reaches the index as anything but a quoted token.
- Results exclude programs and scripts (applications go through `appControl`; a name that matches only programs is reported as such), caches and package folders (`AppData`, `node_modules`, `.git`, `site-packages`, virtual environments, the recycle bin) and the Windows, Program Files and ProgramData folders.
- Resolution never guesses. An item whose name (ignoring case, extension and separators) equals the query is chosen when it is the only such item; when no item is an exact match and exactly one result remains, that one is chosen. Anything else returns `candidates` (at most five: exact names first, then whole-word matches, then newest) as a failed result so the reply model can ask which one. A chosen path then passes through the same checks as any path: it must exist and must not be an executable or script. Opening reports `source: search`.
- Missing paths, empty values, web addresses and other URIs, and executable/script targets are rejected without launching. This tool does not create, overwrite, move or delete files.
- `openPath` with any placement field opens the item and places the window showing it, on the primary display when no monitor is named. The target is resolved (including a name lookup) and the destination validated before anything opens.
  - The program that shows the item is the one Windows' association names (`AssocQueryString`, executable); a folder is File Explorer.
  - When that program is one of the Chromium browsers workspaces support (Chrome opening a PDF, for example), the file opens in a new window of that browser and is found and placed exactly as `openWebsite` places its window (`--new-window`, the shared launch lock), because opening it through the association would add a tab to whichever browser window was last active.
  - Otherwise the item opens once through its association and the program's window is found as `appControl open` finds an application's: a new window of that executable that stays unchanged for half a second, else, after two seconds, the window of that executable that already existed and now shows the item: the only one, or the only one whose title shows the item's name (a program that shows the item in a window it already had, such as a new tab; `reused_window: true`). A program the association does not name by an executable (a packaged app such as Photos) is found as the one new top-level window of any process. Several candidates are never resolved arbitrarily: when exactly one of them shows the item's name in its title (its full name, else its name without the extension), that window is the one showing it, as when a program such as Notepad restores the windows of its previous session around the new one; otherwise the result is ambiguous. Titles are compared locally and never logged.
  - One ten-second deadline covers opening, finding and verified placement. Success is `action: opened_and_placed` with `kind`, `target`, `application` (the program's executable name), `hwnd`, `process`, `monitor`, `zone` (when requested), the verified `rectangle`, `state` and `reused_window`. After an accepted open every other outcome is a partial failure as for `appControl open` (`launch: accepted`, `placement` `failed`, `unverified` or `ambiguous`), and nothing is opened again.
  - The placed window is recorded as a desktop referent under the program's name, never the path.
- Common-folder identifiers are schema data, not natural-language command matching. The existing model path interprets commands in the user's language.
